# 일본어 저장소 브라우저 호환성 검토

## 바뀐 동작

Web Locks가 없다는 이유만으로 일본어 학습을 모두 차단하던 준비 경로를 바꿨다. IndexedDB를 사용할 수 있는 브라우저에서는 공통 직렬화 경로를 통해 계정 준비, 학습 기록 조회, 보충 답안 저장, 원격 기록 적용, 동기화 기준 저장, 로그아웃 정리를 진행한다. 콘텐츠, 직접 선택하는 초급·중급·고급 단계, 기존 진도와 SRS 규칙은 바꾸지 않았다.

IndexedDB를 사용할 수 없거나 차단·중단된 경우에는 일반 학습 화면을 열지 않는다. 일반 화면의 일부 기존 저장 코드는 아직 공통 직렬화에 참여하지 않으므로 화면만 읽기 전용처럼 보이게 하는 것으로는 쓰기를 막을 수 없다. 대신 인증된 계정과 기기 기록의 두 소유자 값이 일치하고 미완료 저장 journal이 없을 때만 수업 수·학습일 수·저장 단어 수·선택 단계의 제한된 요약을 보여준다. 요약은 서버 확인 또는 원자적 전체 기록 조회가 아니다. 기록 변경, 복구, 자동 계정 채택, 클라우드 요청은 요약 화면에서 하지 않는다.

## 공통 저장 순서

- 모든 새 호출은 `yeoni-language-serialization-v1` DB의 `critical-section` object store에 대한 `readwrite` transaction을 사용한다. 읽기 및 복구도 같은 범위에 참여한다.
- transaction을 만든 시점을 획득으로 취급하지 않는다. 해당 store 요청의 성공 이벤트 안에서 동기 로컬 작업만 실행한다. transaction 완료 이벤트 후 결과를 반환한다.
- Web Locks가 있으면 기존 이름의 바깥 잠금도 잡고 IDB 경로로 들어간다. Web Locks가 없어도 같은 IDB store를 사용한다. 새 버전끼리의 Web Locks 유무 혼합 경로는 공통 IDB로 직렬화한다.
- IDB 실패 시 Web Locks만 사용하는 경로로 전환하지 않는다. 그렇게 하면 IDB만 사용할 수 있는 다른 문맥과 공통 잠금이 사라진다. 따라서 Web Locks는 되지만 IDB가 차단된 환경도 쓰기 제한 대상이다.
- IDB에는 학습 내용·계정 정보·잠금 lease를 저장하지 않는다. localStorage lease, 만료된 잠금 탈취, 무잠금 읽기-수정-쓰기를 대안으로 쓰지 않는다.

## 중요한 전환 한계

직전 **Web Locks만 사용하던 버전의 탭**과 새 **IDB만 사용하는 탭** 사이에는 공통 gate가 없다. 새 버전의 Web Locks+IDB 경로가 이 두 독립 경로를 자동으로 중재하는 것은 아니다. 공통 gate를 전혀 쓰지 않는 기존 writer도 보호 범위 밖이다. 새 버전으로 전환할 때 오래된 연이 탭을 모두 닫고 다시 여는 운영 절차가 필요하지만, 현재 코드가 오래된 탭의 종료나 버전을 강제·확인하지는 않는다. 이를 모든 버전·모든 writer에 대한 원자적 저장 보장으로 설명하면 안 된다.

## 오류와 취소

- 시작 전 취소, 열기 실패, 차단된 열기, transaction 생성·요청 실패, 시작 전 버전변경·연결종료에는 저장 콜백을 실행하지 않는다. 지연되다 뒤늦게 열린 연결도 닫고 콜백을 실행하지 않는다.
- IDB 준비 대기는 10초 후 해당 요청만 취소한다. 다른 탭의 잠금을 빼앗는 타이머가 아니다. 이 타이머는 바깥 Web Lock을 얻은 뒤 시작하므로 기존 Web Lock 대기 자체의 시간 제한은 아니다.
- 콜백 시작 뒤 IDB transaction 중단·연결종료가 발생하면 localStorage가 이미 변경됐을 수 있다. `mayHaveChanged`로 구분하고 이 가능성을 안내한다. 자동 재실행하거나 되돌렸다고 표시하지 않는다.
- 저장소를 사용할 수 없다는 오류는 동기화 네트워크 오류와 구분한다. 일반 writer 화면을 닫고 읽기 전용으로 전환하며, 이미 대기 중인 서버 응답의 후속 적용·저장도 중단한다.
- 함수 계약은 PromiseLike 결과를 거부한다. 알려진 async 함수는 실행 전 거부한다. 일반 함수가 뒤늦게 Promise를 반환하면 오용을 탐지할 수 있지만, 이미 시작한 임의의 비동기 코드까지 취소할 수 있다는 뜻은 아니다. 잠금 콜백 안에서는 비동기 작업이나 나중의 저장을 예약하면 안 된다.
- 기존 localStorage journal을 유지한다. IDB transaction은 localStorage 변경을 rollback하지 않는다. journal 복구 중 저장 공간 오류가 나면 journal을 남기고 중단한다. 전원 손실에 대한 완전한 내구성 보장도 아니다.
- 이전 AbortController 구현에서 `throwIfAborted()` 메서드가 없어도 작동하도록 이 저장 경로와 보충복습 hook은 `signal.aborted`를 직접 확인한다.

## 검사와 남은 확인

`tests/fixtures/languageIndexedDB.ts`는 요청·transaction 이벤트의 순서와 취소를 검사하기 위한 합성 모델이다. 실제 IndexedDB 엔진이나 여러 프로세스의 브라우저 저장소가 아니다. 기존 계정·epoch·journal·quota·진도 회귀 검사를 유지하고, 다음을 추가했다.

- Web Locks 없는 계정 준비부터 답안 저장·원격 적용·로그아웃까지의 경로
- Web Locks 유무가 다른 새 문맥의 공통 gate 참여
- 생성 시점과 실제 요청 성공 시점의 구분, transaction 완료 전 결과 반환 방지
- 시작 전 취소, 열기/요청 오류, 차단·시간초과 뒤 늦은 성공, 버전변경·연결종료
- 시작 뒤 중단 시 결과 불확실성, 자동 재실행 없음, 오류가 `undefined`여도 성공 처리하지 않음
- Promise/thenable 타입 계약, 실제 TSX의 읽기 전용 진입·writer 제거·대기 응답 차단·재연결
- 읽기 전용 요약의 무쓰기, 잘못된 소유자·epoch·journal·형식 차단

이 후보의 전체 빌드·전체 회귀는 별도 통합 검사 결과를 따른다. 실브라우저 인증 후 학습, 두 탭 저장, 새로고침, 작은 화면, 서버 반영, 실제 quota/중단 복구는 아직 이 문서의 합성 검사 결과로 대체하지 않는다. 클라우드의 이전 Chromium socket EPERM/localhost 연결 거부 환경은 재시도하거나 우회하지 않았다.

## 독립 실브라우저 가상자료 검사

`node scripts/japanese-storage-compat/build-harness.mjs [출력폴더]`는 실제 `languageStorageLock.ts`를 TypeScript 컴파일하여 작은 정적 검사 묶음을 만든다. 잠금 이름·DB 이름 두 상수만 가상 검사 전용으로 바꾸고 SHA-256을 남긴다. 나머지 저장소 gate 로직은 같다. 운영 DB·학습 키를 사용하지 않는다.

허용된 별도 컴퓨터에서 출력폴더를 localhost `41871` 포트로 제공하고 `http://127.0.0.1:41871/`를 연다. 예: `python -m http.server 41871 --bind 127.0.0.1 --directory <출력폴더>`. 서버 실행과 브라우저 사용은 허용된 환경에서만 한다.

1. ‘새 검사 준비’를 누르고 탭 A, B 링크를 각각 새 탭으로 연다. 두 탭 준비 후 시작한다.
2. IDB-only 모드와 mixed 모드를 각각 수행한다. mixed 모드에서 Web Locks가 실제로 없으면 실패로 기록하고 IDB-only 결과와 구분한다.
3. 최종 횟수 200, 고유 가상 답 번호 200, 두 탭 모두 100개 완료가 맞는지 확인한다. 결과 JSON을 저장한다.
4. 실행한 브라우저/OS·시간·검사 파일 해시와 결과를 함께 남긴다. 검사 탭은 닫는다. 가상 키는 `yeoni-compat-synthetic:` 접두사만 사용한다.

이 검사는 실제 엔진의 독립 gate 검사다. 전체 앱 로그인, UI/기록 복구, 구버전 탭 호환, 클라우드 동기화나 전원 손실 내구성의 완료를 뜻하지 않는다. 이 후보에서는 harness를 생성하고 구문만 검사했으며 실제 브라우저 실행 결과는 아직 없다.
