# Local durable reply candidate — disabled, synthetic only

Hardening candidate based on 425c1ac. Earlier local prototype based on b66eaec. This is a standalone local adapter and SQL draft, NOT a Supabase migration or live backend. The application imports neither. POST /api/yeoni/record-reply remains unconditional 503. No provider or TTS transport exists here. No auth/permission/key settings changed.

## Reused contracts and deliberate boundaries

Reviewed modules/ai-budget-control/{index,persistence}.ts: integer **micro-KRW** (1 KRW=1,000,000), no repeated dispatch grant, unknown commit throws rather than declaring rollback, retained liabilities, no TTL claims, actual settlement never clipped. The new SQL stores cache + receipt + global/account admission atomically; it does not layer a separate account-only CAS over a non-atomic project cap. Existing production budget routes are unchanged.

`LocalDurableReplyClient` accepts explicitly synthetic identities only. It is NOT authentication. A future server must derive owner from verified server session and authorize every operation. Caller-supplied owner or source versions must never be trusted in a live route. This adapter exposes no API, secrets, provider or remote database access.

A trusted publisher supplies a monotonic full-source commit revision and canonical content SHA256. Only complete JSON data may be hashed. Date, Map, Set, custom prototypes, sparse arrays, hidden/symbol properties, accessors, nonfinite values, undefined and cycles are rejected rather than silently converted. Valid JSON canonical bytes and existing hashes are unchanged. Source adapters return incomplete on invalid input; no generation or reservation occurs. Entire persisted originals belong in records; transient synchronization times, selected date ranges, app launch dates and UI state do not. A future backend must write source revision/hash in the SAME transaction as original record changes. This local prototype publishes separately because it has no real record store. Source completeness and ownership must be established upstream. It is not ready for live account integration.

## Transaction and delivery contract

- `reserve`: one database transaction locks/updates global mutex generation, checks session/source, reads exact-version cache FIRST, then inserts unique owner/app/version/pool receipt and checks both account and project pool totals. Invalid/missing quote permits only cache reuse. DB error returns unavailable; never dispatch.
- Same-client `publish` start increments an app-scoped observation generation before validation or asynchronous work. Pending reserve/claim acknowledgements from an older observation are suppressed even if publication fails or has an unknown outcome. Other apps are unaffected. This does not revoke already-delivered grants or fence other processes; that remains a live-integration requirement.
- `claim`: a separate transaction checks source revision/deletion/session again and stores a once-only invocation. It also requires a current nonzero policy and rechecks both project/account liabilities against the current caps. A reserve result is NOT dispatch permission. Never retry a claim grant, including with the same invocation. Lost commit ACK throws; stop. No TTL/reclaim on worker death. Policy rows are locked during reserve and claim; this is not revocation of a grant already returned or fencing of a later external send.
- `finish`: requires matching invocation, preserves entire cost, stores mock-only validated response under exact source version. Finalization checks current source version under the same lock and suppresses an obsolete in-flight result, retaining its liability. A previously completed source version can retain its exact cache, but delivery MUST re-read reserve with current authoritative revision/session. No completion return should directly render a response. Explicit purge prevents late finish from changing deleted tombstones.
- `settle`: records actual micro-KRW without clipping, conflicting repeats fail. Conservative admission uses max(quote,actual); no refunds in this draft. Settlement failure leaves liability untouched. Retaining a quote above actual is intentionally conservative.
- Generation UPDATE prevents stale-snapshot mutex waiters silently passing under stronger transaction isolation; serialization/commit errors fail closed. Actual PostgreSQL locking and partition behavior remain unverified.
- A DB transaction does not guarantee exactly-once external side effects. No provider send occurs in these tests.

## Session, deletion and retention

Logout clears local session immediately and increments durable owner session epoch. Same-owner login can reuse cached answers; another owner cannot. Explicit record deletion/privacy purge is different: trusted publisher MUST call publish(..., erase=true) with a new revision before publishing remaining/new records with a later revision. This clears all app answers and sets a separate `erased` tombstone while preserving each receipt's accounting state, quote, actual cost and claim. Reserve returns deleted for an erased receipt; claim/finalization cannot revive it. Privacy deletion cannot turn a fully settled historical expense back into a pending liability. Ordinary edits publish a new revision/content, retaining old exact-version caches; changes that remove sensitive content must use purge, not edit alone. Delayed lower revisions are rejected. Restoring a purged content hash returns deleted, not a new paid generation. Changed content may get a new reservation only under policy. No automatic TTL or tombstone removal.

Real data retention/deletion durations, legal treatment of content hashes and financial receipts, encryption/RLS/role design, backup erasure and approved restoration/regeneration policy require decisions before activation. Current artifacts contain synthetic data only. Test SQL is not a production permission boundary.

## Budget policy — not activated

Monthly user goals: analysis 7,000 KRW; voice 3,000 KRW. Tests explicitly seed 20% headroom project ceilings 5,600/2,400 KRW and deliberately smaller account ceilings 2,800/1,200 KRW to prove independent limits. Those account ceilings are **test fixtures, not user policy**. No default production policy is configured. Determine project-total versus per-account allocation before live integration.

Admission month comes from DB UTC clock. Cached version identity never includes month/date. Receipts keep original reservation month; settlement does not move it. All prior-month unpriced, pending, uncertain, or above-estimate obligations remain charged against admission in later months, including when their content is erased. Fully priced, completed, non-overestimate historical receipts remain excluded before and after erasure. Current-month charges remain included after erasure. Erasure is never a refund. This intentionally may block indefinitely and requires explicit reviewed reconciliation; it never silently resets capacity. Completed, fully priced, non-overestimate prior-month receipts leave current admission. Billing month/timezone, delayed bill adjustments and reconciliation/credit policies must be decided before activation. Above-estimate liabilities have no automatic expiry in this prototype.

Quote must include all token/character dimensions, FX, tax and uncertainty buffer upstream. No exchange rate/model/provider defaults. Estimates and headroom do not guarantee final invoice absolute limits. Real provider bills, multi-server security, cross-region fencing, network partition and process-crash recovery are not certified.

Tests exercise persistent disk reopen, owner isolation, cache without price, concurrent requests from two adapter clients, duplicate claim, source edits/deletion, late completion, unknown reservation/claim ACK, conservative month carry, settlement conflicts, missing policy/store and disabled API. `scripts/local-durable-reply/process-proof.mjs` uses two sequential OS processes and one disk store, proving receipts/claims/uncertain/tombstones/mock answer survive clean close/reopen. Independent-process simultaneous access, real lock contention, isolation-level races, abrupt crash/fsync recovery and partitions are explicitly unexecuted. ## 2026-11-09 synthetic cost and pre-claim hardening

Independent tests reproduced a missing pre-claim budget check: a pending reservation could still acquire its one-time claim after policy removal, a zero/lower cap, or a newly known above-estimate cost on another request. Claim now checks the current policy and the same conservative liability predicate used by reserve while holding the transaction mutex and policy row lock. A rejected claim retains the receipt and cost. Exact cap equality is allowed. Pool separation, erased/uncertain prior-month carry, and completed fully-priced historical exclusions remain explicit. No new automatic retry or refund exists. An already-returned grant cannot be revoked by this function.

`lib/yeoni/synthetic-cost-quote.ts` adds a disconnected pure **synthetic-only** quote calculator. It takes an explicit complete dimension list and upper usage bounds (including request/tool fees when applicable), rational currency-to-KRW conversion, tax, margin, price/FX validity windows, and a per-request ceiling. It rounds upward using integer arithmetic and rejects invalid/ambiguous dates, expired or future price observations, missing dimensions, coercion/accessor objects, missing own fields, unsafe numbers and overflow. There are no default provider/model prices, exchange rates, tax rates or budget allocations. The 7,000/3,000 KRW values are informational goals; headroom requires an explicit argument and does not configure a live ledger. Synthetic examples are not market price evidence.

The quote tests include a fixture-only handoff of the resulting number into the existing local ledger. **The existing numeric reserve/claim receipt does not persist the quote identity or expiry.** Quote validity is checked when this pure function is called, not durably again at claim. A future complete integration must bind a trusted upper-bound price/FX/billing contract and its deadline to the reservation, recheck it atomically before claim, and prevent bypass through the older numeric API. Do not use this preparation as approval or readiness for real calls. Account allocation, billing month, provider output-limit enforcement, secure authoritative pricing, later invoice adjustments and dispatch fencing remain unresolved.

The independent tests also preserve the limitation that a conflicting later upward settlement is rejected by the existing settlement contract. The candidate does not silently discard, replace, or retry such a financial adjustment. An audited append-only correction/reconciliation mechanism is required before a real provider ledger. PGlite tests do not establish independent PostgreSQL-session concurrency, and no actual provider or production database was used.
