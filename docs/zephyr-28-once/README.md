## Prepared code

`lib/zephyr-28-once.ts` implements a dependency-injected fixed-request runner and bounded HTTP handler factory. No live route imports it, no credential getter/default fetch is provided, and no Edge function is installed. Proposed future URL `/api/tts/once-28` is not registered. HTTP factory refuses non-Preview/wrong-branch/not-installed use; callers can submit only the exact request ID, not text, voice, URL, owner or cost claims. Existing `/api/tts`, `/api/tts/probe`, old61-character/3-slot rows and monthly free-only policy remain untouched.

The draft SQL is outside migrations. It creates a singleton reservation table/function with RLS, no anonymous/authenticated access, service-only reservation and immutable consumed state. No seed is supplied. Owner must be a server-verified authenticated user matched to the installed row. Authorization expires within15minutes of creation; reservation grants10seconds to start sending, and the provider attempt times out after10seconds. Reservation is committed before dispatch, and remains consumed after HTTPerror, malformed response, timeout or process/network uncertainty. No retries/redirects/fallback provider. A new process must consult the same durable row; in-memory protection is not the distributed guard. PGlite queue tests do not establish deployed multi-connection behavior. No database administrator can be prevented by this application from deleting/recreating a table: no such reset operation is exposed or authorized.

Caller disconnect/cancellation is not wired by this prototype: the HTTP factory does not yet forward `request.signal`. Before activation, the adapter must stop before reservation on known cancellation, stop dispatch after a cancelled reservation while leaving it consumed, and propagate abort after send without claiming the provider was cancelled or unbilled. These cancellation integration tests remain an installation gate.

Dependencies are trusted future server adapters, not client flags. Tests use explicitly synthetic permits; those are NOT free-tier or billing evidence. `AUDIO_READY` currently means bounded base64 response passed checks, not actual MP3 decoding or listening acceptance. No audio was generated.
