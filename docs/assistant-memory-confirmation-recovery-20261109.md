# 기억 관리: 확인 요청 수명과 같은 탭 복구

## 범위

기존 F11 기억 관리 화면의 수동 신규·수정·삭제 확인 흐름만 보완한다. AI 자동 기억 추출, DB 스키마·RLS·접근 권한, 운영 배포, 서버 명령 시스템을 추가하지 않는다. 기존 서버의 `assistant_memories`와 `user_app_state.state['ai-fitness-record-reset-assistant']` 읽기 계약을 사용한다.

기준 소스: 검사용 HEAD `ff6ac079e98adb68707923dfbefc3492353ce8a9`.

## 원본에서 확인한 실패

합성 auth/DB로 원본 `review`·`confirm` 코드를 실제 실행했다.

1. 인증 응답을 기다리다가 화면을 떠난 뒤 인증을 해제하면 쓰기 1회, 조회 1회, 늦은 화면 상태 변경 5회가 이어졌다. 원본 확인 함수는 `getUser()` 제한시간과 수명 검사가 없었다.
2. 신규 기억 insert가 서버에 커밋된 뒤 ACK와 확인 조회를 모두 유실시키고 다시 마운트했다. 원본 `change=null`, `attempted=false`로 원래 요청을 잃었고, 같은 내용을 다시 검토하면 새 ID가 생겼다. 합성 서버에 `synthetic-id-1`, `synthetic-id-2` 두 행이 남았다.

어떤 실계정·실자료·원격 Supabase에도 요청하지 않았다.

## 동작 계약

- 인증·각 조회·쓰기 응답에 기본 15초 제한시간을 둔다. SDK가 abort를 무시해도 화면의 대기는 끝난다. abort/시간 초과를 서버 취소로 해석하지 않는다.
- 화면 수명과 owner 세대를 매 await 이후 확인한다. 이탈·로그인 계정 변화 후에는 새 쓰기를 시작하지 않고, 이미 보낸 쓰기의 늦은 응답도 화면·journal 정리에 사용하지 않는다.
- auth callback에서는 동기적으로 기존 요청을 무효화하고 화면을 비운다. 다음 load는 `setTimeout`으로 callback 밖에서 실행한다.
- 같은 계정의 같은 탭 `sessionStorage`에 버전·owner·ID·정확한 before/after·최초/현재 확인 reset marker·attempted 상태를 보관한다. 쓰기 직전에 직렬화한 전체 journal을 저장하고 정확히 다시 읽을 수 있어야 서버 쓰기를 시작한다. 저장 실패·손상·예상 밖 필드·owner 불일치는 fail-closed다.
- 다시 진입하면 목록·reset marker만 조회하고 journal을 복구한다. 이전 요청을 자동으로 재전송하거나 자동 완료하지 않는다. 사용자가 ‘기억 서버 결과 재확인’을 눌러 같은 ID를 읽는다.
- 신규 기억의 재전송은 원래 ID를 사용한다. 수정·삭제는 원래 ID/owner/topic/content before 조건을 그대로 서버 필터에 둔다. 원격 내용이 달라지면 덮어쓰지 않는다. before는 기존 서버의 문자열 스냅샷으로 검증하며 새 입력의 80/2,000자·비어 있지 않음 제약을 적용하지 않는다. 길거나 빈 주제의 기존 행도 줄여 수정하거나 삭제할 수 있다. after에는 신규 입력 제약을 유지한다. 사라진 수정 대상은 insert로 바꾸지 않는다.
- 조회에서 행이 없다는 이유로 journal을 지우거나 새 ID를 발급하지 않는다. 확인 결과가 미반영/충돌이면 보관한다. 미해결 요청을 보류한 채 다른 기억을 관리할 수 있고, 동일 ID 또는 동일 신규 내용의 검토는 기존 요청으로 돌아간다.
- 현재 서버 내용이 요청한 after와 같을 때만 ‘현재 요청한 상태’를 확인한다. 삭제의 경우 부재를 확인한 것이며, 원래 삭제 요청이 반드시 실행됐다고 인과관계를 주장하지 않는다.
- 초기화 marker가 달라지면 부재/일치만으로 완료하지 않는다. ‘초기화 이후에도 같은 ID·내용 반영 확인’이라는 별도 의사 확인 후 현재 marker로 진행할 수 있다. 최초 marker와 원래 ID/before는 유지한다. 초기화 후 수정 대상이 사라졌으면 자동 재생성하지 않고 보류할 수 있다.

## 남는 서버 계약 한계

이는 클라이언트 복구 장치이며 원자적 reset/write나 서버 버전 보장이 아니다.

- reset 조회와 쓰기 사이의 경쟁, 전송 후 초기화와 지연 도착 순서는 서버 트랜잭션으로 묶여 있지 않다. 초기화 전 요청이 늦게 커밋할 가능성은 남는다. 조회 전후 marker 비교는 감지 범위를 늘릴 뿐 그 경쟁을 없애지 않는다.
- before 조건은 현재 내용 기준 compare-and-set이다. 다른 변경 후 정확히 옛 값으로 돌아오는 ABA나 삭제 후 동일 ID로 재생성하는 외부 작업까지 구별하는 version token은 없다.
- 같은 ID insert는 중복 신규 행을 피하는 수단이다. update/delete의 정확히 한 번 실행 또는 과거 명령 취소를 보장하지 않는다.
- sessionStorage는 같은 탭의 새로고침·재진입 복구용이다. 탭 종료·브라우저 저장공간 정리·일부 브라우저 복구 정책에서는 사라질 수 있으며, 기기 간/다른 탭 동기화 저장소가 아니다. 화면에 이 한계를 표시한다.
- 보류된 충돌 요청을 임의로 삭제하지 않는다. 최대 50개 한도 또는 저장공간 문제가 생기면 추가 쓰기를 막고 원인을 표시한다. 저장공간을 지우라고 문제 해결을 자동 실행하지 않는다.

- `tests/assistant-memory-recovery.test.ts`: 20개 통과. 인증/쓰기/조회 지연, 수명 무효화, owner 변경, 저장 전 journal 실패, ACK 유실, 동일 ID 재시도, 조건부 수정/삭제, 초기화 변화, 원래 marker 보존, 숨은 owner/id 필드 차단 등.
- `tests/assistant-memory-page.test.ts`: 10개 통과. 실제 page 함수와 effect를 추출 실행하여 이탈/auth deadline, 중복 클릭, 늦은 callback, 재마운트 read-only 복구, 조건부 필터, A→B→A, 저장 실패, 미전송 확인창 닫기의 쓰기·journal 0건, 이미 전송한 요청 보류 후 journal·ID 보존을 검사한다.
- 변경된 page/helper/tests의 strict TypeScript 및 ESLint 통과.
- 이 파일 작성 시 전체 테스트/Next 빌드와 실제 브라우저 QA는 통합 담당 단계다. 위 합성 함수 시험을 실제 브라우저 완료로 대체하지 않는다.

## 합성 브라우저 QA 항목

실제 제품 page에 가상 client만 주입한 비공개 검사용 경로에서 다음을 검사한다. 이 가상 runtime은 브라우저 새로고침 시 모든 합성 state를 초기화하므로, QA의 재진입은 화면을 나갔다가 다시 들어오는 흐름을 뜻한다. 이 QA로 native sessionStorage의 새로고침 지속성을 검증했다고 보고하지 않는다. 제품의 같은 탭 저장 계약, 합성 저장소를 재사용하는 함수 회귀 시험, 실제 브라우저 화면 재진입 검증은 구분한다.

1. 신규 검토→확인→재조회, 수정 및 삭제의 before/after와 좁은 화면 줄바꿈.
2. 인증 지연 중 이동/뒤로가기 후 해제: 쓰기 0회.
3. 쓰기 커밋 후 ACK 유실 + 조회 실패→화면 나갔다 재진입: 원래 ID 복구, 자동 쓰기 0회, 버튼 재조회로 완료.
4. 미커밋 응답 유실→부재 확인→같은 ID 재전송, 늦은 원래 insert와 함께 도착해도 ID 유지.
5. A→B→A 동안 이전 callback 무시 및 계정별 journal/문구 노출 분리.
6. sessionStorage setItem 실패: 실제 쓰기 0회, 검토 내용 보존.
7. 원격 before 수정 충돌: update/delete 쓰기 0회, 보류 후 다른 기억 관리.
8. 초기화 marker 변경과 행 삭제: 삭제 결과를 성공으로 단정하지 않음, 새 기억은 명시 재확인 후 같은 ID 사용, 기존 수정은 insert로 변환하지 않음.
9. 기록 초기화 전 지연 쓰기를 나중에 해제: 자동 새 ID 없음, 초기화 후 의사를 명시 확인받으며 한계 안내 유지.
