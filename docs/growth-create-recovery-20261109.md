# 자기계발 활동 추가: 저장 결과 재확인

기준 코드: `cbf088bccafa684e4163679a7c5235126471f8c5`, 검사용 브랜치 `agent/fitness-record-priority`.

## 문제와 변경

기존 실제 `addRoutine` 핸들러에서 DB 삽입이 끝난 뒤 응답만 유실되는 경우를 합성 클라이언트로 재현했다. 같은 내용을 다시 저장하면 서버가 서로 다른 ID를 생성해 활동 두 개가 남았다.

- 새 활동에 클라이언트 UUID를 먼저 부여하고, 전송 전에 계정별·탭별 sessionStorage에 그 요청을 보관한다. 저장소가 차단되거나 보관을 확인하지 못하면 삽입하지 않는다.
- 최초 요청과 명시적인 재확인은 같은 ID로만 저장한다. 조회만으로 저장 여부를 확인하고, 이미 존재하면 현재 행을 가져온다. 나중에 바뀐 이름·요일·보관 상태를 덮어쓰지 않는다.
- 결과가 불확실하면 활동 추가를 잠시 막고 같은 요청을 재확인하는 화면을 제공한다. 실제 제품의 같은 탭 새로고침은 sessionStorage에 남은 요청을 읽을 뿐 자동 삽입하지 않는다. 계정이 바뀌거나 화면을 떠나면 후속 콜백이 이전 화면을 갱신하지 않는다.
- 활동 요청 이후 기록 초기화가 감지되면 먼저 같은 ID를 조회한다. 성장 기록 초기화는 활동 자체를 보존하므로 남아 있는 활동은 복구한다. 행이 보이지 않아도 지연 삽입 가능성이 있으므로 ID를 버리지 않는다. 사용자가 ‘초기화 후에도 이 활동 추가’를 별도로 선택했을 때만 같은 ID로 다시 요청한다.
- 클라우드 기록 삭제, upsert, 스키마·권한 변경은 없다. 재시도 정보는 실제 탭을 완전히 닫으면 보존이 보장되지 않는다. 서버의 초기화와 진행 중 요청을 원자적으로 묶는 기능도 아니며, 다른 기기의 저장까지 보장하는 기능은 아니다.

## 검증 범위

집중 시험은 응답 유실·transport 예외·재조회 실패·실제 미삽입 재시도·다른 화면의 수정·보관·계정 전환·저장소 오류·잘못된 요청 정보·초기화·화면 이탈·같은 이름의 별도 정상 활동을 포함한다. 초기화 직후 원래 삽입과 재확인의 완료 순서가 달라도 원래 ID 한 행만 유지하는 합성 회귀를 포함한다.

`/api/qa/growth`는 기존 보호 Preview의 정확한 브랜치에서만 제공한다. 실제 GrowthPage, useGrowthData, 저장 함수를 사용하며 인증·DB·Web Storage·잠금은 가상이다. 운영 및 다른 브랜치는 404, 잘못된 하위 경로도 앱 layout을 열지 않고 404다. opaque sandbox와 CSP로 네트워크·실제 저장소·음성·마이크·외부 이동을 차단한다. 원래 앱의 계정 동기화·배포 보호·보안 설정은 변경하지 않는다.

가상 시험판은 새로고침 시 자료가 사라진다. ‘화면 나가기·돌아오기’로 같은 메모리 요청의 재진입을 검사할 수 있지만 실제 sessionStorage의 새로고침 지속성이나 실제 계정 DB 검증으로 대신하지 않는다. 전체 검사·두 빌드·HTTP 검사·브라우저 결과는 해당 후보의 별도 검증 영수증에 기록한다. 이 문서만으로 실제 계정·기기간 저장·물리 iPhone·전체 앱의 완료를 주장하지 않는다.
